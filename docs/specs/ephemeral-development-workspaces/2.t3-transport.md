## Supported surface

Each VM runs its own server: `t3 serve --host <private-addr> --port <port> --base-dir <dir> --no-browser` (`apps/server/src/cli/config.ts:35-92`; env equivalents `T3CODE_HOST/PORT/HOME/NO_BROWSER`, `config.ts:137-152`).

## Auth and enrollment

- Headless enrollment runs on the VM against its data directory: `t3 auth session issue --token-only --ttl <dur> --label <text> --subject <text> [--scopes ...] --base-dir <dir>` (`apps/server/src/cli/auth.ts:169-202`). Alternatively `t3 auth pairing create --json` (`auth.ts:90-120`) with `POST /oauth/token`.
- Default scopes include `terminal:operate` and `orchestration:operate`, which are equivalent to a shell as the server user (`docs/internals/environment-auth.md:9-16`). Treat the gateway token as VM-root equivalent: store only an OpenBao reference, bind it to VM id and generation, revoke on teardown.
- Bearer and ticket clients are not subject to the browser origin check; cookie sessions are (`EnvironmentAuth.ts:694-714`, `:773-790`).
- DPoP-bound tokens sign the URL, so do not use them behind a rewriting proxy. Use unbound bearer tokens over a private network or TLS.
- Sessions with the `mcp-client` subject are accepted only on `/mcp` (`docs/internals/environment-auth.md:55-66`).

## Proxying

- No base-path setting exists. Do not route under `/vm/<id>/`. Use one origin per VM (wildcard host and certificate), or an API/WebSocket-only gateway that does not serve the T3 web UI.
- No trusted-proxy allowlist exists. `X-Forwarded-Proto: https` is honored (`apps/server/src/requestUrl.ts:9-14`); preserve `Host` or send `X-Forwarded-Host`; pass WebSocket upgrades (`docs/internals/environment-auth.md:68-71`).
- The server's peer-address filter applies only to the background service with no configured host and is not a firewall (`docs/internals/remote.md:58-65`). Bind to a private address and enforce reachability with Hetzner firewall and private networking.
- T3 Connect is an explicit owner opt-in on the existing managed primary VM;
  it is not part of routine gateway sessions. See [the linking and revocation
  contract](../../t3-connect.md). Tailscale Serve and hosted direct pairing are
  still outside the Minicloud adapter contract.

## Opt-in T3 Connect decision (#146)

- Use pinned `t3 connect link --headless --base-dir /workspace/t3`; it prepares
  enrollment for next startup without installing/replacing a service.
  After approval, an explicit, generation-fenced activation restarts only
  `minicloud-t3.service`. Never use bare `t3 connect`/`t3 up`: those can install
  or restart upstream's own background service and interrupt active turns.
- A primary-only, loopback management page captures approval output in memory,
  outside T3's persisted terminal history. A distinct root-only management bearer
  is injected by the gateway after creator/organization-Owner authorization.
  It is not a T3 session. Ordinary sessions retain only their existing four
  terminal/orchestration scopes; do not add `relay:*`, `access:*` or settings scopes.
- Do not spoof a desktop bootstrap subject or loopback authority to bypass
  upstream web linking restrictions (`cloud/linkChecks.ts`).
- Relay-linked T3 clients receive upstream standard client permissions, bypass
  Minicloud gateway authorization/session expiry, and cannot start Minicloud
  compute. Unlink and account-side stale registration removal are separate
  outcomes; already-issued/direct sessions require separate revocation.
  This access grant and the outstanding hosted qualification are documented in
  the linking contract above.

## Quiescence, activity and Git

- T3 exposes thread status (`idle` or a run status), `activeRunId`, `activityRunStatus`, `pendingRuntimeRequest` and `lastError` in the shell snapshot (`packages/contracts/src/orchestrationV2.ts:2075-2092`, `:2125-2140`). This covers agent runs only; terminals, background processes, builds and previews are not included.
- T3 has no admission fence, drain API, quiescence receipt, activity webhook or Git-state API. The gateway must refuse mutating RPC after fencing, poll until idle, and interrupt remaining runs. The Git-save and quiescence checks are Minicloud-owned VM-side checks.
- No supported routing of a user's development-server preview is documented. `apps/server/src/preview/` provides agent-browser features and port detection only; a VM port proxy would be a Minicloud feature with its own authorization.
- Peer links (`docs/internals/remote.md:70-146`) are an agent-to-agent beta and are not used.

## Adapter contract

1. `enroll(vm, generation)`: start `t3 serve` privately, issue the bearer, store only its secret reference, session id and expiry.
2. `discover(vm)`: read the descriptor; require `serverVersion == 0.1.9` and `orchestrationProtocolVersion == 2`; record `environmentId`. Ready means descriptor valid and authenticated session valid.
3. `connectionState(vm)`: authenticated snapshot plus a ticketed WebSocket handshake. An open idle socket is not activity.
4. `taskActivity(vm)`: map snapshot status to running or idle, combined with VM-side terminal, process and keep-awake signals.
5. `route(vm, request)`: authenticate the Minicloud user, authorize VM kind and generation, proxy to the VM's private endpoint with the stored credential. Never accept a client-supplied address or token. Enforce connection, idle and memory limits.
6. Fallback if per-VM origins are unavailable: API/WebSocket-only routing. If neither is workable, keep the fake adapter and record the blocker.

## Unverified; required runtime checks

Not verified: accepted `--scopes` syntax, whether `session issue` needs a running server, its JSON output shape, Node engine requirements, interrupt RPC names, ticket TTL, `/ws` framing, and static asset behavior under a per-VM origin. Run these on a scratch VM or local loopback with synthetic data:

1. Binary and descriptor versions match; protocol is 2; `environmentId` stable across restart.
2. `t3 serve` listens only on the private address; public and sibling-VM access is blocked by firewall.
3. `session issue --token-only` works headlessly; revoked, expired and other-VM tokens are rejected.
4. Ticketed `/ws` works through the gateway; a missing protocol parameter returns 426.
5. Terminal open, write and attach survive proxy restart and VM replacement reconnect.
6. Cookie and bearer behavior through the per-VM origin; subpath proxy fails as expected.
7. Snapshot transitions while a harmless run starts and stops; an idle terminal or socket does not appear as activity.
8. Gateway memory and connection caps under many idle and active sockets; no VM-to-VM or VM-to-control-plane path.
9. Git-save and quiescence evidence are produced by Minicloud checks, never inferred from T3 status.
