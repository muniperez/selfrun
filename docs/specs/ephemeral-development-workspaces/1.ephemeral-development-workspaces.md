# Ephemeral development workspaces: Hetzner proof of concept

Status: Revised specification; partial, unvalidated implementation checkpointed for handoff. Live provider qualification pending.
Owner: Minicloud. Munipages is an example development workload, not the owner of this feature.

## Goal and locked decisions

Reuse the user's existing Minicloud control-plane VPS as the always-available coordinator and T3 gateway. Create appropriately sized coding VMs on demand from prepared images, retain workspace data independently, and delete idle compute. Durable Objects and a separate coordinator VPS are not required.

The control plane hosts Minicloud API/dashboard, durable lifecycle jobs, its existing database/OpenBao, and a separately supervised T3 gateway. Coding VMs supply T3, coding-agent CLIs and a development environment. Users choose the applications, services and additional tools they install or run. The control plane itself and ordinary hosted apps are never eligible for workspace idle deletion.

The default workspace image and lifecycle must not install, initialize or start an application database, emulator or sample application. There are no built-in database roles, data directories, engine-specific shutdown/backup steps or default preview canary. This scope does not change Minicloud's control-plane database or ordinary hosted application/database features.

Each workspace supports at most one active **primary VM** attached to its retained volume, plus multiple concurrent **ephemeral VMs** with no access to that volume. Ephemeral VMs use independent root-disk Git clones; only changes pushed to an authorized Git remote survive their deletion. Both compute kinds are in POC scope.

Execution tracker: [0.execution-plan.md](0.execution-plan.md).

## Repository integration

Reuse organization-owned provider accounts, named plans, OpenBao references, provider action reconciliation, runtime enrollment and Hetzner volume primitives described in [providers](../../providers.md) and [durable storage](../../durable-storage.md). Preserve existing installer, CLI and deployment contracts.

Introduce an explicit DevelopmentWorkspace resource, not an idle flag on every application. Existing plans remain immutable after reservation. A workspace selects from approved plans on each compute generation; it does not mutate an existing plan or silently migrate an ordinary app. Keep volume ownership explicitly bound to organization, workspace, provider account and location. Do not reuse app-volume identities by guessing app IDs.

The POC is opt-in, Hetzner-only, single-region per workspace, and linux/amd64. Infrastructure configuration must not require the Munipages checkout or an installed T3 client to run deterministic tests.

## User experience and scope

An authorized user creates a workspace, chooses a registered image, an approved size profile and persistent volume capacity, then selects Start. Show provisioning, attachment, enrollment and readiness separately. Open terminal/agent session and preview links only after their relevant readiness checks pass. Show preserved-data status, last activity, pending shutdown, current size and ongoing storage charges.

Provide Standard (target 8 GiB RAM) and Heavy (target 16 GiB RAM) profiles mapped by the operator to real Hetzner SKUs with explicit CPU counts and location. These are initial defaults, not measured capacity guarantees. Reject unavailable capacity without silently selecting another account, architecture, region or higher price.

Support primary VM Start, Status, Stop compute, Cancel pending idle stop and Change size on next start through the API and CLI, with a minimal dashboard workspace list/detail. A running size change explicitly drains and recreates compute; never promise live memory/CPU hot resizing. Automatic load-driven resizing, spot instances, cross-region migration, billing users, public anonymous previews and workspace-data deletion are outside the POC.

## Additional ephemeral VMs and Git durability

Users can launch multiple ephemeral VMs under a workspace, whether its primary VM is running or stopped. Each launch selects an approved image/profile, an authorized repository and an explicit base ref resolved to a commit SHA. Give each VM its own identity, generation, unique work branch, enrollment token, task leases, activity deadline and lifecycle operation. Ephemeral VMs are independently startable and stoppable, and are subject to the same VM concurrency and spend caps as primary VMs. Display each VM's kind, size, state, task and Git publication status in the dashboard/API/CLI; gateway links must select the specific VM.

An ephemeral VM clones the repository onto its disposable root disk. It receives no volume attachment, filesystem export, primary-VM SSH credential, shared Docker socket, workspace backup access or storage-serving route. Enforce this in provider allocation, enrollment claims, network rules and gateway authorization; a missing mount alone is not isolation. Deny lateral access to the primary VM and sibling VMs by default. Workspace membership alone must not grant a VM access to another VM's files or secrets. Supply only explicitly selected task secrets and least-privilege repository credentials, with bounded lifetime and revocation on teardown. No implicit inheritance of persisted primary-VM credentials or ignored files.

Prepared images supply common tools, but each ephemeral VM checks out its own repository state; primary-VM uncommitted files are unavailable. Changes move between machines only through authorized Git remotes and explicit fetch/review/merge. Unique branches prevent competing agents from overwriting each other. No automatic default-branch pushes, force pushes, branch merges or pull-request creation. Push authority must be explicit in the task/user policy; do not infer permission merely from starting a VM.

A local commit is not durable after VM deletion. Before ordinary idle or manual destruction, stop task admission, finish/drain work, freeze repository writes and inspect every registered checkout/worktree. Record repository identity, base SHA, branch, final HEAD and verified remote ref/SHA. Every final commit must be reachable from its authorized remote ref, and local tracked modifications and untracked files must be resolved. Revalidate after freezing writes; a previous successful push is insufficient if further edits occurred. Submodules and Git LFS content require explicit support and verification or must block a claim that their data is saved.

If changes are uncommitted, commits are unpushed, push authority is missing, the remote is unavailable or verification fails, enter an actionable **Awaiting Git save** state and keep the VM billed. Show the reason and let the user authorize a push, resolve the state, or explicitly choose **Destroy and discard local data**. Never silently auto-commit/push arbitrary files or turn credential failures into data loss. Ignored files (including local databases, caches, secrets and artifacts) are not saved by Git: disclose this at launch and before destructive discard. Record acknowledgement of that ephemeral-data policy; never add ignored secrets just to make teardown pass. Process quiescence and generation-bound deletion fencing still apply.

Abrupt VM/provider loss can lose everything since the last verified push; Git-based persistence is not crash-proof. Encourage task milestones to publish to the authorized branch, but never replay ambiguous pushes blindly or assert that a local commit is remotely saved. Do not create volume snapshots, backups, or private file-upload channels as a hidden persistence fallback for ephemeral VMs. The coordinator may retain bounded sanitized lifecycle metadata and Git receipts, not a copy of their workspace filesystem. Relaunch means a new clone from a selected remote commit; it does not resume the old root disk or local databases.

Primary idle shutdown and each ephemeral VM's idle shutdown are independent. Stopping the primary does not stop its siblings. A separate explicit Stop all compute action enumerates affected VMs and honors each one's task and save guards. Resizing an ephemeral VM follows save/delete/reclone semantics. Primary storage retention and single-writer guarantees are unchanged.

## Control plane and T3 gateway

Run coordination as bounded jobs on the existing Minicloud worker and store state in its persistent database. Run the T3 gateway as a separately supervised service/container with CPU/memory limits, log rotation and health checks. Reserve capacity for API, database, secrets and routing. Gateway deployment must use a pinned compatible release; do not bake credentials or install floating releases. Packaging must remain opt-in and must not claim a currently unpublished Minicloud release is available.

Define an adapter for workspace enrollment, endpoint discovery, session/terminal/preview routing, connection state and task activity. Inspect actual T3 capabilities before implementation; document the supported transport and authentication rather than inventing APIs. If the available T3 version cannot separate gateway and remote execution, expose this as an integration blocker and retain a tested fake adapter. Do not run coding tasks on the control plane as a fallback.

Authenticate and authorize each terminal, agent session and preview connection against its organization, workspace, VM identity and compute generation. Use an outbound authenticated connection from the VM where supported; otherwise use a restricted private management channel. Never expose raw user-service ports, the Docker socket, agent management endpoints or arbitrary internal URLs publicly. Route only explicitly registered user-created workspace services. A stable workspace URL shows a sleeping/starting state and starts compute only after an authorized explicit action; crawlers and health probes must not allocate machines.

Scope the gateway so long-lived terminal/preview traffic cannot exhaust coordinator resources. Persist session metadata and file-backed transcripts on durable storage as appropriate; an in-memory terminal process is not preserved across deletion. Display interrupted tasks and offer a new run or provider-supported resume, never automatic replay of commands with external side effects.

## Data and image contract

A workspace has one independently retained Hetzner volume, accessible only to its primary VM and mounted at a stable path such as /workspace. It contains repositories including untracked/ignored edits, designated agent session state, user-selected application data, publication artifacts and workspace configuration. Document every durable path and bind mount. Root disk, temporary files and expendable caches are disposable. Root-home files are not implicitly durable. Enforce stable UID/GID and preserve user files and data formats; installing or migrating user applications is not a hidden resume step.

Mount by verified provider volume identity and filesystem UUID. An existing volume is never formatted on resume. Refuse wrong ownership, missing/wrong mount, unexpected filesystem or local-directory fallback. Exactly one compute generation may write the volume. Pin replacement VMs to the volume's provider account and compatible location. No automatic forced detach.

Build reproducible, versioned Hetzner snapshot images with a manifest containing source revision, architecture, OS/tool versions and build provenance. Include the selected development toolchain, Chromium libraries, runtime supervisor and bootstrap agent. Munipages' illustrative image needs Node 24 and .NET 10; Minicloud development may use its own pinned Node version. Provide an image build/validation recipe and registration workflow. Live image creation is an explicit paid operation, not part of default CI.

Generalize images before capture: remove cloud-init instance state, machine identity, host keys, build-time tokens, agent logins, workspace data and credentials. Generate per-instance identity and host keys on boot. Keep the root image compatible with the smallest offered profile. Primary starts reuse the image and volume without recloning; ephemeral starts reuse the image but make a fresh authorized Git clone. Neither requires reinstalling the complete toolchain every time.

Store provider credentials only through existing control-plane OpenBao references. Supply short-lived, single-use, generation-bound enrollment credentials to VMs; redact bootstrap material and revoke it after use. Workspace secrets must be scoped and encrypted under an explicitly documented storage/key policy; keys must remain recoverable outside disposable compute. The POC must not claim volume encryption supplied by the provider without verification. Persist only intentionally selected user credentials, never control-plane/provider secrets.

A retained volume is not a backup. Define generic encrypted off-host workspace backup and restore hooks, independently recoverable keys, retention and restore verification. Do not assume a particular application or database engine. State the consistency guarantee honestly: application-specific consistency requires explicit user-selected lifecycle integration; unknown running work blocks unsafe shutdown rather than being killed. Hetzner server snapshots exclude attached volumes. Normal idle teardown preserves the volume and requires a durable quiescence receipt, but does not require copying the entire volume on every stop. Backup freshness/failure is separately visible; a policy requiring a fresh backup must block deletion if it fails. Live qualification includes a restore into a separate volume.

## Lifecycle and reconciliation

Persist lifecycle state per VM, rather than one server/generation slot for the whole workspace. The primary and ephemeral VM kinds are explicit and immutable. Persist desired state separately from observed phase: Stopped, Provisioning, Attaching, Bootstrapping, Ready, Draining, Deleting, Recovering, Awaiting Git save or Blocked. A failed attempt records its phase, resource evidence and retry classification; it must not imply no provider resources exist.

Minimum records: workspace ownership and policy; VM identity/kind and per-VM generation; ephemeral repository/base/branch and verified remote-save/discard receipts; immutable image version; selected/current plan; volume identity/location/filesystem; monotonically increasing compute generation; provider server/action IDs; operation IDs and idempotency keys; enrollment digest/expiry; gateway endpoint; readiness; task leases; activity timestamp; shutdown deadline; quiescence/backup evidence; resource inventory and sanitized audit events.

The following attachment and storage flow applies to the primary VM. Ephemeral VMs use the same allocation/enrollment/reconciliation machinery but skip all volume creation/attachment/mount/detach phases and require the Git save or explicit discard receipt before deletion. They cannot transition into storage phases.

1. Start validates authorization, account, image compatibility, quota and configured cost/concurrency caps. Persist the generation and allocation intent before contacting Hetzner.
2. Reconcile a labeled server using organization/workspace/VM/generation/operation identity. An ambiguous create timeout must trigger discovery in the same account before another create. Ambiguity or multiple matches blocks with operator-visible evidence.
3. Verify the previous writer is stopped and fenced, attach the retained volume, await provider actions, verify/mount the filesystem, enroll the new generation and start the workspace supervisor.
4. Mark Ready only after required checks and gateway registration. Old-generation callbacks, activity and endpoint updates are rejected.
5. Stop fences new task admissions and drains admitted tasks. Quiesce T3 and explicitly registered user workloads, flush files and unmount the volume. Unknown user work blocks shutdown; do not stop arbitrary processes or run engine-specific commands. Persist a generation-bound quiescence receipt.
6. Detach safely, delete the exact owned VM, reconcile confirmed absence, and clean up only owned ephemeral IP/DNS/enrollment resources. Never delete the retained volume or shared image. Report Stopped only once compute absence and retained storage are verified.
7. Resume creates a new VM from the selected image, reattaches the same volume and starts services. Resizing follows this same workflow with a compatible approved plan and explicit restart notice.

Workers use database leases and fencing, with bounded retries/backoff. Locks alone cannot fence a VM that retains volume access: never start a replacement writer until provider evidence confirms the previous one is stopped/detached. Reconcile provider action completion, not just request acceptance. Lost deletion responses must be retried by exact recorded identity, without affecting replacements.

On control-plane restart, scan incomplete operations and reconcile owned resources before acting. On network partition or missing heartbeats, mark Unknown/Blocked; absence of a heartbeat is not proof of idleness or quiescence. Do not delete an unreachable VM automatically. Expose continued cost and manual recovery options. Inventory reconciliation must never collect resources based on a broad name prefix alone.

## Idle policy and cost controls

Default inactivity timeout: 360 minutes (6 hours). A saved workspace override of 1–10,080 whole minutes applies to both VM kinds and takes precedence over the operator's `DevelopmentWorkspaces:IdleGraceMinutes` default. A workspace may instead choose Keep running, which disables automatic idle stop for its VMs (with explicit cost disclosure) without bypassing manual stop, quotas or spend caps. Useful user activity and registered running agent/build jobs keep a VM active. Health checks, log streaming, passive preview traffic and an open but unused WebSocket do not. Provide a visible keep-awake lease for long tasks and tools without automatic integration.

Active tasks use renewable authenticated leases bound to workspace, VM, generation and task ID, with bounded expiry and completion/cancellation records. The supervisor enumerates running work before drain; expiry alone must not kill a task. Every Minicloud-launched coding/build task must be registered; external tools need an explicit lease or cannot be safely idle-stopped. Never infer idle solely from low CPU.

The inactivity timeout is not a VM lifetime limit. After it elapses, publish a separate shutdown countdown without fencing admissions. Useful activity or a timeout increase can cancel a premature countdown before claim. At claim, recheck the effective timeout, fresh heartbeat and unresolved work before fencing admission; a settings change does not undo a claimed shutdown. Gateway drain and runtime quiescence have their own safety checks. Once deletion is committed, queue an authorized Start for the next generation.

Hetzner server billing continues while powered off and ends on deletion; usage is rounded up to whole hours. Show that repeated short sessions may each incur an hour. Account separately for retained volumes, snapshots, backups, IPs, traffic and the shared control-plane baseline. Do not claim idle is free. Obtain rates from configuration/current provider catalog, preserve currency and rate timestamp, and label calculations as estimates.

Enforce global, per-organization and per-workspace active VM limits (both VM kinds count), provider quotas, allowed profiles and configurable global and per-organization spend caps. Workspace records and distinct active workspaces have no separate count limit. A cap prevents new allocation and raises an alert; it does not silently destroy active work. POC cleanup defaults to dry-run and excludes control-plane resources, ordinary application servers, retained volumes and shared images.

## POC acceptance

- Run a primary VM and at least two ephemeral VMs concurrently in one workspace; also launch ephemeral compute while the primary is stopped. Verify independent leases, idle deadlines, size profiles, budget accounting and gateway routes.
- Prove ephemeral VMs cannot attach/read the retained volume, invoke primary storage APIs, read backups or reach primary/sibling files through network/gateway paths; reject forged VM-kind/generation claims.
- In two separate Git clones, publish to distinct authorized branches, destroy the VMs and verify changes from fresh clones. No force push or default-branch mutation occurs. Primary uncommitted files and ignored secrets never appear in ephemeral clones.
- Dirty trees, untracked files, unpushed commits, unavailable Git remotes and missing push authority block automatic destruction. A clean remotely verified checkout permits deletion; explicit discard requires recorded user intent. Test edits after a push and during drain, remote-ref mismatch, stale save receipts and unsupported LFS/submodules.
- Relaunch of ephemeral compute recovers only remote Git state. Its ignored local data is not preserved, and UI clearly states this before launch/destruction. No hidden workspace backup or shared filesystem is introduced.

- Synthetic provider tests cover concurrent Start/Stop, duplicate requests, create/delete timeout after success, worker crash at each phase, stale generation callbacks, lost task lease, active jobs, shutdown cancellation, account/volume mismatch, quota exhaustion, failed quiescence and unattached storage.
- API authorization tests deny cross-organization workspace/volume/session access. Verify token expiry, replay rejection, secret redaction and preview route isolation.
- Existing deployment/plan/storage behavior remains unchanged. Migrations preserve existing rows and tests demonstrate ordinary hosted apps/control-plane resources cannot enter workspace deletion.
- Boot from a registered minimal environment image without toolchain reinstall or automatic application-stack provisioning. Create committed, uncommitted and ignored fixture files, designated agent state and a file-backed transcript. Stop/delete compute, start a replacement, and verify exact preservation and usable T3/CLI tooling.
- Perform at least three stop/resume cycles and an approved profile change; demonstrate one writer and no extra VM/IP leak. Verify clean storage mounts and recover after a simulated coordinator restart.
- Demonstrate an idle stop, an active-agent exemption and an idle open-terminal case. A partition must block unsafe deletion and produce actionable status.
- Verify authenticated T3 terminal routing, an explicitly user-created preview workload, and reconnect to the replacement generation using a real supported T3 version. Do not ship the test workload as a default product service. Report adapter limitations explicitly.
- Record cold/warm readiness time, image-build time, peak coordinator/gateway memory, task memory, billed server lifetimes and retained storage costs. Initial POC target: resume ready within five minutes over five measured trials; report misses rather than hiding image installation time.
- Restore a backup into a separate volume and verify representative data. Document retention, recovery limitations and manual cleanup.

Default automated checks use fakes/local fixtures and allocate no paid resources. Live Hetzner/image/T3 qualification requires an explicitly configured isolated project, budget and credentials through secure input; source implementation is not hosted acceptance. No deployment or purchase is authorized by this specification alone.
