MiniCloud runs coding agents and hosts apps on your servers

Work on a Git repository with Codex or Claude Code in a Linux VM you control. You or your agent can use the MiniCloud CLI to deploy Docker services, check their logs, and put a web app on your own domain.

Set up MiniCloud View source on GitHub

Run coding agents on a Linux VM

Enable Dev Environments to start coding VMs. Open T3 Code, the browser interface for the agent and terminal running on the VM. Clone a repo and run your tests. VM images can include Codex, Claude Code, or GitHub Copilot CLI. Use your own account to sign in to the agent.

Stop the VM and resume later with your repo and T3 sessions on its disk. To open a development preview in your browser, ask your administrator to register the service and its port in the workspace configuration.

Deploy Docker services

Run minicloud init in an app repo and select the services to deploy. By default, minicloud deploy builds images with Docker Buildx, publishes them to MiniCloud's registry, and deploys the selected services.

One app can have a public frontend, a private API, and a worker. Update them separately, give staging its own environment, and attach an HTTPS domain to a public service. The dashboard shows deployment history and which services are running.

Set up MiniCloud

A MiniCloud instance is your installation of MiniCloud. Its dashboard, API, container registry, and deployment worker run together on one virtual private server (VPS). It has its own HTTPS dashboard address, such as cloud.example.com. It creates and manages separate VMs for coding and app hosting in your Hetzner, DigitalOcean, or Vultr account. Your provider bills you for those resources.

If someone already runs MiniCloud for your team, get the dashboard address and sign-in details from them and sign in from your terminal.

  1. Install MiniCloud on a VPS

    The current installer is for testing from source. On Linux (x64 or ARM64) or Apple Silicon macOS, install Git, Python 3.11 or later, the .NET 10 SDK, and OpenSSH. You also need a VPS provider account, an SSH key, and DNS access. After installation, export the one-time setup token and use it at the dashboard’s /setup page to create the first account.

    Build and install a test server

    1. Install the CLI. Use the installer in the checkout so the CLI matches the server code you’re about to package.

      git clone https://github.com/muniventures/minicloud.git
cd minicloud
export PATH="$HOME/.local/bin:$PATH"
MINICLOUD_INSTALL_MODE=source MINICLOUD_VERSION="$(git rev-parse HEAD)" \
  MINICLOUD_INSTALL_DIR="$HOME/.local/bin" sh install.sh

      Package the server for a test install. There is no published server release yet. The Python command creates the archive the CLI will send to the VPS. Save the printed sha256 for the deployment plan, and the seed ID for the next step.

      umask 077
seed_dir="$PWD/.local/artifacts/local-seed"
mkdir -p "$seed_dir/reports"
python3 -B scripts/self-hosting/local_source.py package \
  --version 0.0.1-local.1 --output "$seed_dir/source.tar.gz"
minicloud seed new-id

      To resume in a new terminal, return to this checkout, restore PATH and seed_dir as shown above, and restore the variables and seed_local function in the VPS creation step. Keep the original archive and seed ID.

    2. Set the provider and domains. Save this DigitalOcean example to $seed_dir/seed-config.json. Set providerAccount to DigitalOcean account followed by account.uuid from your provider’s authenticated GET /v2/account response. Fill in the seed ID, region, size, and domains. Keep the seed ID if you need to resume. Put the provider token in $seed_dir/provider-token. Both files need mode 0600. Hetzner and Vultr account formats are in the seed guide.

      {
  "schemaVersion": 1,
  "seedId": "REPLACE_WITH_SEED_ID",
  "provider": "digitalocean",
  "providerAccount": "DigitalOcean account REPLACE_WITH_ACCOUNT_UUID",
  "region": "nyc3",
  "size": "s-2vcpu-2gb",
  "domain": "cloud.example.com",
  "appDomain": "apps.example.com",
  "serverVersion": "server-v0.0.1-local.1",
  "architecture": "linux/amd64",
  "initialCreationIntent": "one-authorized-creator-no-unresolved-create"
}

    3. Review the cost and create the VPS. Set the archive hash and SSH key path. If your key has a passphrase, use ssh-add and add --use-ssh-agent to the seed commands. The plan shows the account, region, size, and cost. Copy its approval digest into the apply command. If the create request times out, check the provider before retrying.

      archive_hash='REPLACE_WITH_ARCHIVE_SHA256'
ssh_key="$HOME/.ssh/id_ed25519"
provider_token="$seed_dir/provider-token"

seed_local() {
  minicloud seed "$@" --config "$seed_dir/seed-config.json" \
    --report "$seed_dir/reports/seed-report.json" --ssh-key "$ssh_key" \
    --local-source "$seed_dir/source.tar.gz" --source-sha256 "$archive_hash"
}

seed_local plan --credential-file "$provider_token" --new-seed
seed_local apply --credential-file "$provider_token" --new-seed \
  --approve REVIEWED_CREATION_DIGEST

    4. Verify the VPS and finish the install. Get the VPS's ed25519 SSH host fingerprint independently through the provider console. In the same config, remove initialCreationIntent and add target with the server ID and IPv4 from the create report and the verified fingerprint. Use the new plan's digest to continue on that VPS.

      "target": {
  "serverId": "REPLACE_WITH_SERVER_ID",
  "ipv4": "203.0.113.10",
  "hostFingerprint": "SHA256:REPLACE_WITH_VERIFIED_ED25519_FINGERPRINT"
}
      seed_local plan --credential-file "$provider_token"
seed_local apply --credential-file "$provider_token" \
  --approve REVIEWED_CONTINUATION_DIGEST

    5. Open the dashboard. Follow the report's DNS instructions for cloud.example.com and api.cloud.example.com. Confirm both respond over HTTPS. Export the recovery files and setup token, then open https://cloud.example.com/setup. Enter the token, create your account, and sign in. Keep the recovery files encrypted off the VPS.

      minicloud seed export --config "$seed_dir/seed-config.json" \
  --report "$seed_dir/reports/seed-report.json" --ssh-key "$ssh_key" \
  --recovery-dir "$seed_dir/private-recovery" --setup-token

    Source installation and recovery guide · First operator account

    In the dashboard, open Plans → Provider accounts and add your cloud account. Then choose Plans → Add plan and select a region and server size. You'll pick this plan when you create an app.

  2. Sign in from your terminal

    The minicloud command needs to know which dashboard to use. Replace cloud.example.com with your dashboard hostname. If you just built MiniCloud, use the CLI you built with it. For a team server, use the CLI your team provides or install a compatible version below.

    Install the CLI for an existing server

    Use Linux (x64 or ARM64) or Apple Silicon macOS with Git, jq, and the .NET 10 SDK. The server advertises the CLI builds it accepts. This command selects and prints a compatible build after you enter the dashboard hostname.

    dashboard=cloud.example.com
revision=$(curl -fsS "https://api.$dashboard/api/instance" |
  jq -er 'first(.cliCompatibility.sourceRevisions[]? |
    strings | select(test("^[0-9a-f]{40}$"))) //
    error("No compatible CLI commit listed")')
printf '%s\n' "$revision"

    Install the build selected above. If the server lists no compatible build or uses private source, ask the person who runs it for the CLI.

    (
  set -e
  : "${revision:?Run the previous block first}"
  installer=$(mktemp)
  trap 'rm -f "$installer"' EXIT
  url=https://raw.githubusercontent.com/muniventures/minicloud/main/install.sh
  curl -fsSL "$url" -o "$installer"
  MINICLOUD_INSTALL_MODE=source MINICLOUD_VERSION="$revision" \
    MINICLOUD_INSTALL_DIR="$HOME/.local/bin" sh "$installer"
)
export PATH="$HOME/.local/bin:$PATH"

    Add $HOME/.local/bin to your shell’s startup PATH to keep using minicloud in new terminals.

    CLI installation and Windows instructions

    Sign in with the CLI

    minicloud instance add work cloud.example.com
minicloud login

    work is a name for this server on your computer. Complete sign-in in the browser, then return to your terminal.

  3. Deploy your first app

    Open your app’s Git checkout with Docker and Buildx running. Use a supported Node.js, .NET, or Spring Boot service, or include a Dockerfile in each service folder. Run minicloud init to select or create an app, choose the folders and plan, and write minicloud.yml. Your first deployment can create a billable VPS under that plan.

    minicloud init

    Before deploying, review minicloud.yml. Keep the app ID that init wrote and check each service’s folder, Dockerfile, port, and public access. Here is an example services section for a public frontend and a private API:

    services:
  web:
    sourcePath: web
    dockerfile: web/Dockerfile
    port: 3000
    public: true
  api:
    sourcePath: api
    dockerfile: api/Dockerfile
    port: 8080
    public: false

    Deploy the configured services:

    minicloud deploy

    For a public service, use the hostname under your configured app domain. With Cloudflare DNS management enabled, MiniCloud creates the record. Otherwise open the run in Deployments and follow its DNS message: create an A record for the printed hostname pointing to the app VPS IP. After DNS resolves and deployment completes, open the public URL.

    Configure service folders, ports, and Dockerfiles

  4. Check and update your app

    • Deployments shows whether a deploy is queued, running, or finished. Open a deployment to see its progress and logs.
    • Apps → your app → Services shows which services are running and their addresses. Choose the environment first if you have more than one.
    • Apps → your app → Logs shows runtime output when log collection is enabled. Set regular variables in minicloud.yml with env. Store secret values under Secrets and reference them with secretEnv.
    • Apps → your app → Domains is where you add a hostname, verify it with DNS, and attach it to a public service.
    • App settings has controls to delete an app or environment. Back up data before deleting it and confirm the VPS is gone in your provider console. Retained volumes can still incur charges.

    After changing code or configuration, run minicloud deploy again to update the changed services. Use minicloud status --watch to follow a deploy and minicloud logs my-app for runtime logs when log collection is enabled.

    Deployment status and runtime logs

  5. Start a coding VM

    The person who runs MiniCloud must enable Dev Environments and configure a qualified provider image, a plan, and the workspace gateway. Then open Dev Environments → Create dev environment, choose a size and location, and create it.

    When the VM is running, choose Connect to T3 → Open T3. In T3, sign in to your agent under Settings → Providers and open a project. Stop the VM from the dashboard when you're done. Retained disks still incur storage charges.

What runs on each server

The instance VPS hosts the dashboard, API, registry, and worker. PostgreSQL stores control-plane state, and OpenBao stores secrets. An app VPS runs your containers. A separate coding VM runs T3 Code and the agents on its image. The workspace gateway routes browser sessions to that VM. OpenTelemetry log ingestion is optional.
